# Security deployment requirements

- Configure the same randomly generated `HEXAWAVE_AI_SERVICE_TOKEN` in the backend and AI service. Never commit the real value. In production, the AI service rejects every route except `/health` without this token; the backend will not make AI requests if its token is missing.
- Keep the AI service on a private network and allow inbound access only from the backend. The service token supplements network isolation; it is not a replacement for it.
- Project-wide AI maintenance sends only bounded supported text files to the model. It excludes known secret filenames, files matching the credential-pattern filter, symlinks, generated/dependency directories, and oversized files; this heuristic is not a complete secret scanner, so review project files before requesting AI changes.
- The IDE's autonomous task can edit project files, run configured tests/builds, and make up to three repair attempts. It cannot deploy, modify production, enable trading, or invoke external actions. Until an OS/container sandbox is available, use this feature only with trusted projects in a non-production environment.
- Trading is disabled by default and can only be enabled by the King administrator. The UI switch is not the only control: the backend blocks trading routes and quote-triggered automation while disabled. Live broker execution remains unsupported.
- Generated project installation, builds, and runtime execution are disabled when `HEXAWAVE_ENV`, `NODE_ENV`, or `APP_ENV` is `production`. They execute untrusted code and dependencies; do not enable them on a production host until they run in a separately isolated OS/container sandbox with restricted network, filesystem, CPU, and memory access.
- Rotate any credentials that have been exposed, and store production secrets in a managed secret store rather than source control or image layers.
- Razorpay credentials (`HEXAWAVE_RAZORPAY_KEY_ID`, `HEXAWAVE_RAZORPAY_KEY_SECRET`, and `HEXAWAVE_RAZORPAY_WEBHOOK_SECRET`) are server-only. Never put them in frontend environment variables, source files, browser responses, or chat. Immediately revoke and replace any credential previously pasted into chat.
- Billing starts disabled. King configures prices, Razorpay plan IDs, and credit usage from the admin Billing settings. Checkout remains unavailable unless credentials and the webhook secret are configured and King enables billing. Live credentials additionally require `HEXAWAVE_RAZORPAY_LIVE_ENABLED=true`; sandbox credentials must be used for development and tests.
- Billing records currently use a local JSON file store (`HEXAWAVE_BILLING_STORE`). Razorpay checkout is deliberately disabled in production until transaction-safe shared storage and atomic payment/credit fulfillment are implemented. Do not enable production charges with this file store.
- Payment completion is trusted only after server-side signature verification and a Razorpay API lookup or verified webhook. The frontend callback alone does not mark an order paid. AI credits and paid company requests are fulfilled only after that verification; credit balances are account-scoped.
- These safeguards reduce specific risks but are not a guarantee that the application is secure. Production still requires a threat model, hardened hosting, monitoring, backups, and independent security testing.
