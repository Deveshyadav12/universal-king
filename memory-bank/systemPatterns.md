# System patterns

- **High-level layout**: NestJS `backend/src` modules (`auth`, `projects`, `ai`, `crm`, `trading`, `king`) + Next.js `frontend/app`.
- **Data flow**: Market quotes → `evaluateBaselineRule` → journal + optional paper fill if strategy is running and armed. King requests stay `pending` until admin `approve`/`reject`.
- **Project maintenance**: The IDE posts project-wide instructions through the ownership-checked NestJS endpoint to the AI service. AI context is limited to supported UTF-8 text files; known credential files/content, symlinks, generated directories, and files over the context limits are excluded. Validate every model-produced path and replacement before writing any changes.
- **Autonomous IDE task**: One explicit task request triggers project-wide edits, static checks, supported runtime tests, build validation, and at most three repair attempts. Return changed files and check results; do not bind this loop to deployment, production changes, trading, or other external actions.
- **Auth/UI separation**: `admin` is King; post-login and dashboard routes lead to `/king`. Regular accounts use `/workspace` and a separate company-request page. Request history is scoped to the authenticated requester; approval and queue actions stay admin-only.
- **Tenant workspaces**: Each company has its own generated workspace ID. Its CEO and invite-code employees share that tenant's projects and IDE data; individual accounts get separate workspace IDs. `/workspace` renders the authenticated tenant's company dashboard or the individual's private dashboard. Only the company's CEO receives the employee roster and invite-management controls; APIs derive tenant access from the authenticated user rather than URL parameters.
- **Billing and paid actions**: King alone configures catalog prices, recurring Razorpay plan IDs, and credits per AI action. Checkout is disabled by default; server verifies payment signatures and fetches provider payment state before crediting an account or adding a company request to the approval queue. Razorpay webhooks use the raw request body and event IDs for signature verification and replay protection. Do not treat client callbacks as payment proof.
- **Billing storage constraint**: Payment, ledger, and webhook idempotency currently use a local JSON store, so all gateway checkout is blocked in production until transactional shared storage is implemented.
- **Patterns to follow**: Pure rule functions in `baseline.strategy.ts`. Operator gates (`requireApproval` / `armed`). Role checks in the global `AuthGate` and API authorization decorators.
- **Patterns to avoid**: Silent live orders, stacking longs, shipping offensive security tooling.
